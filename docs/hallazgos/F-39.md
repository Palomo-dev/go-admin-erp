# F-39 — Fuga cross-tenant en políticas sin filtro de organización

**Severidad:** Alta
**Estado:** Documentado
**Fase:** Fase 2

## Qué es

Tres políticas RLS permiten lectura entre organizaciones porque su
predicado es siempre verdadero o depende de una variable de sesión
suplantable.

## Evidencia

### Patrón `organization_id IS NOT NULL` (siempre true)

| Tabla | Política | Predicado |
|---|---|---|
| `variant_types` | Allow operations on variant_types by organization | `organization_id IS NOT NULL` |
| `variant_values` | Allow operations on variant_values by organization | `EXISTS (SELECT 1 FROM variant_types vt WHERE vt.id = variant_values.variant_type_id AND vt.organization_id IS NOT NULL)` |
| `product_notes` | product_notes_org_isolation | `auth.role() = 'authenticated' AND organization_id IS NOT NULL` |

`organization_id IS NOT NULL` es siempre true para cualquier fila con
organización asignada. No filtra por la organización del usuario. Cualquier
usuario autenticado puede ver notas, tipos de variante y valores de
variante de cualquier organización.

Hoy no hay exposición material (1 y 0 filas en variant_types/values), pero
el patrón está en producción y se copia a la siguiente tabla que alguien
cree.

### `current_setting('app.current_org_id')` suplantable

| Tabla | Política | Predicado |
|---|---|---|
| `payment_qr_sessions` | payment_qr_sessions_org_isolation | `organization_id = current_setting('app.current_organization_id')::integer` |
| `reservation_blocks` | reservation_blocks_org_isolation | `organization_id = current_setting('app.current_org_id')::integer` |
| `reservation_customers` | reservation_customers_isolation | `reservation_id IN (SELECT ... WHERE organization_id = current_setting('app.current_org_id')::integer)` |

Tres políticas híbridas usan `auth.uid() OR current_setting(...)` como
fallback:

| Tabla | Política |
|---|---|
| `folios` | folios_org_isolation |
| `rates` | rates_org_access |
| `reservations` | reservations_member_update |

`current_setting('app.current_org_id')` se setea vía `supabase.rpc('set_config', ...)`
desde el cliente (`reservationBlocksService.ts:55`, `ratesService.ts:8`).
Un cliente malicioso puede llamar `set_config('app.current_org_id', '999')`
y ver datos de otra organización.

Si nadie hace SET de la variable, la tabla queda inaccesible. Si la setea
el cliente, es suplantable. Ninguna de las dos es aceptable.

## Causa raíz

Las políticas usan `current_setting` en vez de `auth.uid()` /
`organization_members` porque el flujo de reservas y QR sessions no siempre
tiene un usuario autenticado en el contexto RLS. Pero la solución correcta
es filtrar por `organization_members` (para usuarios autenticados) o usar
service_role (para flujos sin usuario), no exponer la tabla a `public` con
una variable suplantable.

## Arreglo

1. `variant_types`, `variant_values`, `product_notes`: reemplazar
   `organization_id IS NOT NULL` por el patrón estándar
   `organization_id IN (SELECT organization_id FROM organization_members
   WHERE user_id = auth.uid() AND is_active = true)`.
2. `payment_qr_sessions`, `reservation_blocks`, `reservation_customers`:
   cambiar a `TO authenticated` y filtrar por `organization_members`. Los
   flujos sin usuario (webhooks) ya usan `getSupabaseAdmin()` (service_role),
   que bypassa RLS.
3. `folios`, `rates`, `reservations`: eliminar el fallback a
   `current_setting` y dejar solo `auth.uid()` / `organization_members`.

## Verificación

Después del arreglo, verificar con:
```sql
SELECT tablename, policyname, qual FROM pg_policies
WHERE schemaname='public'
AND (qual ~ 'organization_id IS NOT NULL'
  OR qual ~ 'current_setting.*app\.current_org');
```
Debe retornar 0 filas.

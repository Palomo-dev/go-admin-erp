# F-45 · fn_create_journal_entry invierte el IVA en ventas

**Severidad:** CRÍTICA
**Estado:** Corregido en producción (2026-09-19); histórico neutralizado (2026-09-23)
**Bloque:** A (bloqueante de lanzamiento)

## Hallazgo

`fn_create_journal_entry` siempre pone la línea de impuesto al DÉBITO. En
ventas, `2405` ("Impuestos y Contribuciones por Pagar") es una cuenta de
PASIVO: el IVA cobrado al cliente aumenta el pasivo con la DIAN, así que debe
ir al CRÉDITO.

## Fragmento exacto de la función

```sql
-- Linea de debito (principal)
VALUES (v_entry_id, p_debit_account, p_memo, p_amount - COALESCE(p_tax_amount, 0), 0);

-- Linea de debito (impuesto)  ← SIEMPRE débito, sin importar si es venta o compra
VALUES (v_entry_id, p_tax_account, 'IVA - ' || p_memo, p_tax_amount, 0);

-- Linea de credito
VALUES (v_entry_id, p_credit_account, p_memo, 0, p_amount);
```

## Asiento actual (incorrecto para ventas)

Para una venta con base 1.000.000 + IVA 190.000:

```
1105 Caja     débito  1.000.000     ← p_amount - p_tax (debería ser p_amount)
2405 IVA      débito    190.000     ← PASIVO al débito = la DIAN te debe a ti
4105 Ventas   crédito 1.190.000     ← sobrevaluada en el IVA
```

El asiento cuadra (1.190.000 = 1.190.000), por eso ninguna validación lo
detecta. Pero las tres líneas tienen el monto o el signo equivocado.

## Asiento correcto para ventas

```
1105 Caja     débito  1.190.000     ← p_amount completo
4105 Ventas   crédito 1.000.000     ← p_amount - p_tax
2405 IVA      crédito   190.000     ← p_tax al CRÉDITO (aumenta pasivo)
```

## Asiento correcto para compras (sin cambio)

En compras, el IVA descontable SÍ va al débito (es un activo/credito fiscal):

```
1435 Mercancía  débito  1.000.000
2405 IVA        débito    190.000     ← correcto: IVA descontable al débito
2205 Proveedores crédito 1.190.000
```

## Los 5 llamadores que pasan p_tax_amount

| Función | Tipo | IVA debe ir a | ¿Cambia? |
|---|---|---|---|
| `fn_auto_journal_sale` | Venta | CRÉDITO | Sí → `p_tax_is_credit := true` |
| `fn_auto_journal_sale_pos` | Venta POS | CRÉDITO | Sí → `p_tax_is_credit := true` |
| `fn_auto_journal_purchase` | Compra | DÉBITO | No (actual, correcto) |

### Verificación de nota crédito y anulación

Las reglas de `sale_credit_note/created` y `sale/voided` tienen las cuentas
invertidas respecto a la venta original:

- Venta: débito 1105/1305, crédito 4105
- Nota crédito: débito 4105, crédito 1305
- Anulación: débito 4105, crédito 1305

Si la venta pone IVA al crédito (nuevo), la reversa debe poner IVA al débito
(actual). Por eso nota crédito y anulación NO cambian.

## Arreglo

Diseño aditivo (no rompe los 41 llamadores existentes):

```sql
-- Nuevo parámetro con DEFAULT false (mantiene comportamiento actual)
p_tax_is_credit boolean DEFAULT false
```

- `false` (actual): débito = p_amount - p_tax, IVA débito, crédito = p_amount
- `true` (ventas): débito = p_amount, IVA crédito, crédito = p_amount - p_tax

Ambas variantes cuadran. Solo se actualizan los 2 llamadores de venta.

## Por qué bloquea F-42

Hoy este bug casi no se ejerce porque solo 73 de 2.881 facturas tienen
`tax_total > 0`. El arreglo de F-42 hace que TODAS las facturas nuevas lleven
IVA. Si se despliega F-42 sin F-45, el bug latente se convierte en error
contable sistemático en cada factura emitida desde el día uno.

F-42 y F-45 se despliegan juntos. Nunca F-42 solo.

## Incidente de despliegue — sobrecarga de función (2026-09-19 ~22:46 UTC)

La primera migración usó `CREATE OR REPLACE FUNCTION` para agregar
`p_tax_is_credit`. Postgres no permite agregar parámetros con REPLACE: crea
una **sobrecarga**. Quedaron dos `fn_create_journal_entry`:

- 12 args (vieja, IVA invertido)
- 13 args (nueva, correcta)

Las 49 llamadas con notación nombrada que omitían `p_tax_is_credit` calzaban
con ambas → `ERROR 42725: function is not unique`. Como corren dentro de
triggers, la excepción abortaba la transacción: los usuarios no podían crear
facturas, ventas ni pagos.

**Remedio aplicado:** `DROP FUNCTION` de la firma de 12 args. Las 49 llamadas
viejas resuelven contra la de 13, omiten `p_tax_is_credit`, cae en `false`
(comportamiento previo). `sale` y `sale_pos` pasan `true` (IVA al crédito).

**Ventana de caída:** ~22:46 a ~22:54 UTC (8 minutos).

**Lección (regla nueva):** cambiar la firma de una función compartida no es
una migración aditiva. Antes de aplicar:
1. Contar los llamadores.
2. Ejecutar la sonda de resolución antes y después.
3. Confirmar que `pg_proc` tiene exactamente una fila para ese `proname`.

El archivo de migración en el repo se corrigió: `DROP FUNCTION` de la firma
vieja + `CREATE` de la nueva, en ese orden, en la misma transacción.

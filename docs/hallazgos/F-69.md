# F-69 · La exportación a banca online no descargaba nada, y la conciliación decía haber conciliado sin escribir una fila

**Severidad:** Crítica (la interfaz afirmaba un hecho contable falso)
**Estado:** Corregido y verificado (2026-09-24). La conciliación real **no** se
construye aquí: se retira la mentira y se deja el encargo escrito.
**Origen:** Revisión de la exportación a banca online de cuentas por pagar.

## Hallazgo

Dos defectos en la misma pantalla
(`src/components/finanzas/cuentas-por-pagar/ExportarBancaModal.tsx` y su
servicio). El segundo es mucho peor que el primero.

### a) La tabla `public.bank_files` nunca existió

`CuentasPorPagarService.exportarParaBancaOnline` insertaba en
`public.bank_files`. Verificado por MCP el 2026-09-24:

```sql
select to_regclass('public.bank_files');  -- NULL
```

No había tabla equivalente con otro nombre. En el esquema viven
`bank_accounts`, `bank_transactions`, `bank_transfers`, `bank_reconciliations`
y `bank_reconciliation_items`, y ninguna sirve para esto: describen cuentas,
movimientos y conciliación de extractos, no lotes de pago exportados. También
faltaban `bank_file_transactions` y `payment_approvals`, los otros dos tipos de
`types.ts` sin tabla detrás.

El insert fallaba siempre con `42P01`, el método lanzaba, y el modal lo llamaba
**antes** de generar el blob:

```ts
const archivoData = await CuentasPorPagarService.exportarParaBancaOnline(...);  // revienta aquí
const contenido = generarContenidoArchivo(cuentas, formatoBanco, formatDate);   // nunca se llega
```

Resultado para quien usaba la pantalla: **la exportación a banca online no
descargaba ningún archivo, jamás**. Solo «Error al exportar».

### b) La conciliación era un `setTimeout` que decía que sí

```ts
const conciliarPagos = async (registros: BankFileTransaction[]): Promise<void> => {
  return new Promise((resolve) => {
    setTimeout(() => {
      console.log('Conciliación simulada de', registros.length, 'registros');
      resolve();
    }, 1000);
  });
};
```

Y a continuación, en `handleConciliar`:

```
title: "Conciliación completada"
description: `Se conciliaron ${registrosConciliados.length} pagos correctamente`
```

No se escribía **nada**: ni un `payment`, ni un movimiento de cartera, ni un
`accounts_payable.balance`. Quien creyera el mensaje daba por pagadas facturas
que seguían abiertas al 100 %. Esto no es una funcionalidad incompleta: es la
interfaz afirmando un hecho contable que no ocurrió.

Además `procesarArchivoBanco` parte el archivo en el navegador y deja **todos**
los registros en `status: 'unmatched'`, sin cruzarlos nunca contra una cuenta
por pagar: ni siquiera existía el intento de cruce que el botón decía rematar.

### c) Tres defectos menores que salieron por el camino

1. **`generarContenidoArchivo` no casaba con ningún banco.** El `switch` iba
   sobre `'bancolombia' | 'davivienda' | 'bbva'`, pero el desplegable enviaba
   `'bancolombia_txt' | 'davivienda_csv' | 'bbva_excel'`. Ninguna rama entraba:
   los cuatro formatos caían en el CSV genérico del `default`. Elegir
   «Bancolombia TXT» bajaba un CSV con encabezado.
2. **`bbva_excel` anunciaba `.xlsx` sobre texto separado por `;`.** Excel lo
   abre con advertencia de formato corrupto. Pasa a llamarse «BBVA CSV» con
   extensión `.csv`; el valor `'excel'` sigue en la unión de tipos para el día
   que exista un escritor de xlsx de verdad.
3. **El rastro describía un archivo que nadie tuvo.** `file_name` y `file_type`
   eran `.csv` / `'csv'` fijos aunque se hubiera descargado un `.txt`.

## Corrección

### La tabla, con su rastro

Migración `supabase/migrations/20260924170000_bank_files_rastro_de_exportacion_a_banca.sql`
(+ `..._bank_files_privilegios_minimos` para los privilegios por defecto),
reversión en `supabase/rollbacks/`, aplicadas con `apply_migration`.

Las columnas son **exactamente** las que el código ya escribía
(`BankFileRecord` en `types.ts`), con los tipos que la unión de TypeScript
declara:

| Columna | Tipo | Justificación |
|---|---|---|
| `id` | `uuid` PK, `gen_random_uuid()` | el tipo declara `id: string`; `accounts_payable.id` también es `uuid` |
| `organization_id` | `integer NOT NULL` FK → `organizations(id) ON DELETE CASCADE` | multi-inquilino; `organizations.id` es `integer` |
| `file_name` | `text NOT NULL`, `char_length` 1..255 | nombre real del archivo descargado |
| `file_type` | `text NOT NULL CHECK in ('csv','excel','txt','xml')` | copia literal de la unión de TS |
| `records_count` | `integer NOT NULL DEFAULT 0 CHECK >= 0` | cuentas del lote |
| `processed_count` | `integer NOT NULL DEFAULT 0 CHECK >= 0` | hoy siempre 0: la conciliación no existe |
| `status` | `text NOT NULL DEFAULT 'pending' CHECK in ('pending','processing','completed','failed')` | copia literal de la unión de TS |
| `upload_date` | `timestamptz NOT NULL DEFAULT now()` | instante, no día |
| `processed_date` | `timestamptz NULL` | opcional en el tipo (`processed_date?`) |
| `created_by` | `uuid NOT NULL` FK → `auth.users(id)`, sin acción en borrado | idéntico a `payments.created_by`; el rastro sobrevive a la baja de la persona |
| `created_at` | `timestamptz NOT NULL DEFAULT now()` | única columna de más; es el `created_at` de casa |

**Sin `branch_id`, decidido y justificado.** El lote agrupa cuentas por pagar de
cualquier sucursal —el modal las carga sin filtro, y su propio comentario ya lo
decía— así que no hay una sucursal dueña. Y hay una razón de más peso: las
tablas con `branch_id` de este esquema llevan encima una política **RESTRICTIVE**
`app_branch_access(branch_id)` (`accounts_payable`, `bank_accounts`,
`bank_transactions`…). Inventarle una sucursal al lote escondería parte del
rastro a quien no tenga acceso a esa sucursal, que es exactamente lo contrario
de para lo que sirve una auditoría.

RLS por pertenencia, con el patrón de la casa
(`organization_id in (select organization_id from organization_members where
user_id = (select auth.uid()) and is_active is true)`, el mismo de
`bank_reconciliations`, con `(select auth.uid())` envuelto como exige la nota de
coste de RLS):

- `SELECT` por pertenencia activa.
- `INSERT` por pertenencia activa **y** `created_by = (select auth.uid())`: la
  escritura sale del navegador con la sesión del usuario, así que RLS es la
  única barrera y nadie puede firmar un lote con el id de otra persona.
- `UPDATE` por pertenencia (para marcar `processed_*` el día que haga falta).
- **Sin política de `DELETE` y sin `grant delete`**: un rastro de auditoría no
  se borra desde la interfaz.

**Trampa que costó una segunda migración:** los privilegios por defecto de
Supabase conceden `ALL` sobre cada tabla nueva a `anon`, `authenticated` y
`service_role` **en el momento del `CREATE TABLE`**. Un `grant` posterior no
quita nada. Tras la primera migración, `authenticated` conservaba `DELETE`,
`TRUNCATE`, `TRIGGER` y `REFERENCES`. `DELETE` lo frenaba RLS (0 filas), pero
**`TRUNCATE` no pasa por RLS**: cualquier sesión autenticada podía vaciar el
rastro de los 85 inquilinos con una sentencia. Hay que `REVOKE ALL` primero y
volver a conceder lo justo. Estado final: `authenticated` →
`SELECT, INSERT, UPDATE`; `anon` → nada.

### El archivo primero, la auditoría después

`exportarParaBancaOnline` **ya no lanza nunca**. Devuelve
`{ registrado, archivo, error }` y el modal la llama **después** de descargar.

El criterio: el archivo es lo que la persona vino a buscar, y la auditoría no
puede quitárselo. Pero un fallo de auditoría tampoco puede pasar en silencio, así
que hay tres avisos en cascada: `logError` en consola, `registrado: false` con el
motivo en el retorno, y un *toast* destructivo en pantalla —«El archivo se
descargó, pero no quedó registrado»— con el error concreto. Nadie puede pensar
que quedó anotado si no lo está.

### La pantalla deja de mentir

- `conciliarPagos`, `handleConciliar` y el botón «Conciliar Pagos» **eliminados**,
  con el *toast* de éxito. No queda ni botón muerto ni flujo a medias: en esa
  pestaña, el pie del diálogo solo tiene «Cerrar».
- La pestaña pasa de «Conciliar Archivo» a **«Revisar archivo del banco»**, y
  se abre con un `Alert` destructivo: *«La conciliación automática todavía no
  existe»* + el texto de `AVISO_SIN_CONCILIAR`, que dice sin rodeos que nada de
  lo que se ve se ha aplicado, que ninguna cuenta se ha marcado como pagada, que
  no se ha creado ningún pago, y por dónde se registra un pago de verdad.
- La tabla se titula «Registros del archivo (N) — vista previa», cada fila se
  marca **«Sin cruzar»** (antes ponía el literal inglés `unmatched`) y debajo se
  repite que no se ha aplicado nada.
- El *toast* de lectura pasa de «Archivo procesado» a «Archivo leído … No se ha
  conciliado nada: es solo una vista previa».
- `accept` baja de `.txt,.csv,.xlsx` a `.txt,.csv`: los `.xlsx` no se leen, el
  parser trabaja sobre texto.

### El catálogo de formatos, extraído

`FORMATOS_BANCO` y `generarContenidoArchivo` salen a
`src/components/finanzas/cuentas-por-pagar/formatosBanca.ts`: el servicio los
necesita para que el rastro describa el archivo real, y el modal no se puede
cargar en un test de Node. Cada formato lleva ahora `extension` y `tipo`, y el
`switch` casa con los valores del desplegable.

## Lo que haría falta para la conciliación de verdad — NO construido

Encargo cerrado para más adelante. Cinco piezas.

**1. Dónde vive el archivo leído.** `bank_files` ya guarda la cabecera del lote.
Falta `bank_file_transactions` (el tipo `BankFileTransaction` ya existe y
tampoco tiene tabla): `bank_file_id`, `organization_id`, `reference`, `amount`,
`transaction_date`, `description`, `status`
(`unmatched | matched | processed`), `matched_payment_id`,
`matched_account_payable_id`. Misma RLS por pertenencia y mismo `revoke` a
`anon`. Sin ella, el cruce no es reproducible ni auditable: hoy el parseo vive y
muere en la memoria del navegador.

**2. Cómo se cruza un registro del banco con una cuenta por pagar.** En orden,
parando en el primer acierto y **dentro de la misma organización siempre**:

- a. Por **referencia exacta** contra el número de la factura de compra:
  `bank_file_transactions.reference` ↔ `invoice_purchase.number_ext` →
  `accounts_payable.invoice_id`. Es el campo que la exportación escribe en la
  columna REFERENCIA de los formatos BBVA y genérico, así que el banco lo
  devuelve tal cual. Es el único cruce con el que se puede ser automático.
- b. Por **NIT del proveedor + importe exacto + ventana de fechas**:
  `suppliers.nit` ↔ el NIT que el archivo trae en su columna, `amount` =
  `accounts_payable.balance` al céntimo, y `transaction_date` dentro de ±N días
  del lote. Si devuelve **más de una** cuenta candidata, **no se decide sola**:
  queda `unmatched` y se propone a una persona.
- c. Todo lo demás: `unmatched`, con el motivo. Nunca se inventa una pareja por
  proximidad de importe.

Restricciones que el diseño debe respetar: el cruce se hace en la base (una RPC
transaccional, no N llamadas desde Node — regla 7), la organización sale de la
sesión y no del cuerpo de la petición (regla 5), y un mismo
`bank_file_transactions.id` no puede cruzarse dos veces (UNIQUE parcial sobre
`matched_payment_id`, o estado `processed` irreversible).

**3. Por dónde entra el pago. ATENCIÓN A LOS DISPARADORES.**

> **La única escritura permitida es un `INSERT` en `payments`.** La base
> recalcula el saldo de la factura y la cartera **por disparador**. Escribir
> `accounts_payable` (o `accounts_receivable`) a mano **descuenta dos veces**:
> una el `UPDATE` manual y otra el disparador. Y un `INSERT` en `invoice_sales`
> ya crea su cartera por sí solo, igual que un `INSERT` en `sales` con estado
> `paid` crea la comisión. Nunca se toca la cartera a mano.

Así que la conciliación **no** debe «marcar la cuenta como pagada». Debe crear
el pago y dejar que la base haga el resto. Y el pago no se inserta a pelo: ya
existe la ruta que sabe hacerlo con su moneda, su método y su caja
(`CuentasPorPagarService.registrarPago` / el flujo de `RegistrarPagoModal`).
Una segunda implementación diverge en semanas.

Antes de escribir el primer `INSERT`, hay que **inventariar los disparadores
vivos sobre `payments` y `accounts_payable`** y hacer la prueba en seco con
`DO … RAISE EXCEPTION`, contando filas de `payments`, `accounts_payable`,
`journal_entries` y `cash_movements` antes y después. Un pago de conciliación
que además genera asiento contable duplicado es el mismo error de F-01 y F-48
con otro traje.

**4. Qué decide una persona y qué decide la máquina.** La conciliación automática
solo debería aplicar el cruce (a) —referencia exacta y única—. Los cruces por
importe se **proponen** y alguien los aprueba: es dinero, y un falso positivo
cierra una deuda que sigue viva. La pantalla necesita, por tanto, tres estados
visibles: cruzado y aplicado, cruzado y pendiente de aprobación, sin cruzar.

**5. Idempotencia.** Subir dos veces el mismo archivo del banco no puede pagar
dos veces. Con `bank_files` ya hay dónde apoyarse: un hash del contenido por
organización, o al menos rechazar un lote cuyas referencias ya estén en estado
`processed`.

## Verificación

**Prueba en seco de la tabla**, con `DO … RAISE EXCEPTION` para que la
transacción aborte y no persista nada. Dos organizaciones distintas con dos
personas sin pertenencia cruzada (elegidas por consulta, no cableadas):

```
 1 insert propio ............ OK
 2 insert de otra org ........ RECHAZADO 42501
 3 insert suplantando ........ RECHAZADO 42501   (created_by de otra persona)
 4 file_type fuera del CHECK . RECHAZADO 23514
 5 delete .................... RECHAZADO 42501
 6 truncate .................. RECHAZADO 42501
 7 lectura del autor ......... A ve 1
 8 lectura desde otra org ..... B ve 0
```

Antes de la segunda migración, los pasos 5 y 6 salían `filas borradas=0` y
`TRUNCATE PERMITIDO`: ese fue el hallazgo de los privilegios por defecto.

**Sin residuos:** `select count(*) from public.bank_files` → 0 antes y después.
`get_advisors(security)` no reporta nada sobre `bank_files`.

**Red de regresión:** `src/__tests__/finanzas/bancaOnlineCuentasPorPagar.test.ts`,
30 pruebas en cinco bloques: el rastro y sus columnas, el fallo de auditoría que
no lanza y sí avisa, las cuatro plantillas de banco, la ausencia de conciliación
fingida y el contrato de la migración. El bloque que importa a largo plazo es
**«ningún conciliador puede resolver sin escribir»**: recorre el módulo, localiza
toda función cuyo nombre hable de conciliar, le extrae el cuerpo por conteo de
llaves y falla si simula trabajo (`setTimeout`, `new Promise(resolve`,
`Promise.resolve()`) sin tocar la base. Con el código anterior falla; con este,
pasa.

## Daño histórico

**Ninguno que reparar, y se puede afirmar con certeza.** `bank_files` no existía,
así que no hay filas que corregir. Y la conciliación simulada **no escribía
nada**: por definición no dejó un solo dato malo en la base. El daño fue
íntegramente de información —gente que creyó haber conciliado pagos— y no es
reparable desde el código: si alguna organización usó esa pantalla creyendo el
mensaje, sus cuentas por pagar nunca se movieron y siguen exactamente donde
estaban. Conviene avisarlo por soporte, no por migración.

## NO VERIFICADO

- **La descarga en un navegador de verdad.** Todo lo de este arreglo se
  comprobó con pruebas en Node y con el esquema real por MCP; nadie abrió la
  pantalla y pulsó «Exportar Archivo». El orden (descargar → registrar) está
  verificado por posición en el código, no por observación.
- **El formato exacto que espera cada banco.** Las cuatro plantillas ahora sí se
  distinguen entre sí, pero que el ancho fijo de Bancolombia o el separador de
  Davivienda sean los que su portal acepta **no está confirmado con
  documentación de los bancos**. Antes de este arreglo la pregunta no tenía
  sentido, porque los cuatro bajaban lo mismo.
- **`bank_file_transactions` y `payment_approvals`** siguen sin tabla. El tipo
  `PaymentApproval` de `types.ts` no tiene nada detrás; no se tocó porque
  `AprobacionPagosModal` no entra en este encargo.
- **El día del nombre del archivo** lo calculan dos sitios: el modal con
  `getToday()` del contexto y el servicio con `todayInTz(resolveTimezone(org))`.
  Ambos salen de `organizations.timezone`, pero una exportación lanzada
  exactamente en el cambio de día podría anotar un día distinto del que lleva el
  archivo descargado. No se ha reproducido.
